# CLOUD-03.4D1 — Contrato remoto v3 por bloques
Decisión: dividir ciphertext ya generado por codec v3 en bloques máximos de 4 MiB, no recifrar, no usar TUS en este corte. Supabase recomienda TUS para archivos >6 MB (https://supabase.com/docs/guides/storage/uploads/resumable-uploads); bloques de 4 MiB mantienen una transferencia estándar acotada y permiten reintentar cada objeto. No es TUS ni reanudación dentro del bloque. Rutas canónicas archive/operation/asset/index, create-only futuro. Header versionado incompatible con fixture, metadatos/nonce/ciphertext, hash por bloque y por activo, tamaños, orden original. Sin títulos/nota/ID local en claro. Validación exacta, 100 activos/35 MiB cada uno/128 MiB agregado, manifiesto 256 KiB. El lector reconstruye ciphertext, verifica hashes, devuelve paquete v3; decodeV3Record verifica AES-GCM y manifiesto antes de materializar. El helper de servidor verifica un bloque independiente, no demuestra autenticidad del contenido ni posesión de clave. La función makeV3Wire clona el paquete y conserva vistas; uso de RAM sigue siendo alto, especialmente iOS. No adoptar en producción sin mediciones.
Backend D2: intención durable inmutable, chunks registrados y atestados por servicio de confianza tras lectura real, RLS de rutas exactas y gate cerrado, CAS transaccional con historial/recibos, cuotas de bytes reservados (incluyendo staging), limpieza controlada y auditoría de permisos. El hash de activo completo requiere verificación cliente; si se exige prueba servidor usar digest incremental de bloques en orden sin depender del cliente. Prohibir UPDATE/DELETE desde clientes y mantener objetos inmutables hasta commit; cualquier GC debe coordinarse con lock de intención. No reutilizar el bucket fixture ni habilitar escrituras reales. Límites de Free deben verificarse antes de activar cuota definitiva; cada revisión ocupa almacenamiento y egress.
