# CLOUD-03.5C1 — Contrato incremental candidato (offline)
Decisión: conservar v3 y wire v1 sin cambios de formato. Nuevo formato archivito-sync-incremental-v1, nuevo dominio AAD para activos inmutables [domain,version,archiveId,memoryId,assetId,birthRevision,keyId]. Nonce aleatorio por nuevo activo; no recifrar un activo inmutable ni reutilizar nonce para texto distinto. Metadata por revisión usa primitiva AES-GCM existente y manifiesto de formato nuevo. Cada manifest autentica referencia exacta (UUID, birth revision, nonce, tamaño ciphertext, SHA-256 ciphertext), MIME, SHA-256 plaintext y ubicación página/cara. No publicar hashes de plaintext. Reutilización sólo misma página/cara, tipo/tamaño/hash de plaintext iguales, predecessor inmediatamente anterior y autenticado contra identidad esperada externa (no inferida del propio header). Lectura verifica descriptor, bytes, GCM, plaintext hash y validación de imágenes. No deduplicación global, no migración implícita v3. Revela igualdad entre revisiones por identidad estable y tamaños; límite de privacidad aceptable sólo dentro de mismo recuerdo, sujeto a revisión. Evita recifrar imágenes iguales; sigue leyendo y hasheando blobs locales para comprobar cambios. Sin red, sin dist/UI ni cambios Supabase.
Delta incluye metadata nueva y lista completa de refs, sólo ciphertext de nuevos activos. Preflight de servidor simulado comprueba refs heredadas exactas del predecessor y tamaños/hashes de nuevas; no puede verificar contenido ni autenticidad del manifiesto cifrado. La autoridad de predecessor y CAS deberá venir de backend; el helper no es autorización ni prueba de commit. Sin eliminación física: historial sigue referenciando activos antiguos. El protocolo de red futuro deberá implementar tabla inmutable de activos por archivo/memoria/clave, paths independientes de operación, referencias transaccionales de revisión, reserva de cuotas para nuevos bytes + manifiesto, staging/attestation, CAS/receipt, RLS y GC coordinado con locks/referencias y retención; nunca borrar objetos aún referenciados. Migración explícita del snapshot completo v3 a primera revisión de nueva cadena (con evidencia/rollback, no reutilizar ciphertext v3 incompatible). Outbox incremental deberá persistir exactamente el delta y predecessor, reconciliación y caché verificada; sin publicar ni activar gate en este corte. 
Cinco pruebas Node: metadata-only 0 bytes de imagen nuevos, una foto sustituida, nueva hoja/remoción, historial, rechazo de manipulación/clave/scope/predecessor, faltantes/extras. Imágenes sintéticas, sin benchmark real. Validadores de metadata/crop compartidos con v3 para preservar las restricciones. Siguiente 03.5C2: transporte incremental simulado con CAS/recibos y retención, después contrato wire y SQL rollback.
