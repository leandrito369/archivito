# CLOUD-03.5C3B3D.4E.3 — Stack Supabase local aislado
Fecha 2026-11-26. Base #57 ff16d3c7377c8cf0cfcd3978338ad3e4eb226ae9, CI 4/4, runtime cerrado 13/13 HTTP y 7 grupos ACL/admin. E.1/E.2 aprobados en sus laboratorios; no promoción.
## Diseño y límites
Supabase CLI 2.122.0 fijada (release estable 23/10/2026); evita cambios de CLI v3 y config.jsonc por defecto de v3.4.0. Docker en runner efímero Ubuntu. La instancia local se crea en directorio temporal fuera del repo con project_id aleatorio, sin supabase link, sin credenciales hosted, sin copiar .env, config ni datos. El harness rechaza ejecución fuera de CI, versión diferente, contenedores preexistentes del ID o puertos ocupados. API HTTP loopback fija, sin proxy ni redirect; SQL sólo docker exec al contenedor recién creado. Variables de entorno limitadas y HOME nuevo; secretos locales capturados sólo en proceso, no se imprimen. Se registra imagen/tag de contenedores y versión PG, no Env ni status completo. CLI genera config.toml; PG17 y verify_jwt=false exclusivamente en función candidata (handler sigue autenticando con getUser). No se usa service key cloud ni se publica en frontend. Docker puede descargar imágenes y Edge dependencias; no se afirma aislamiento de red total. SDK fuente fijado 2.119.2, lock transitivo e imágenes digest pendientes.
Empaquetado: copiar seis módulos fuente de app/server al _shared/archivito manteniendo import graph; adaptar sólo ruta de import del entrypoint, sin cambiar lógica. supabase start arranca stack local con función configurada. Se verifica que Edge/Auth/PostgREST/Storage/DB reales estén activos, sin dobles. Si falla import o inicio, detener, revisar CI; no fallback a simulación. 
## Aprovisionamiento y criterios E.3
Crear archivos/membresías equivalentes estructuralmente al remoto (DDL local explícito, FK a auth.users, roles, RLS); crear A/B/C nuevos con Admin API local, contraseñas aleatorias efímeras; aplicar 5 fuentes SQL exactas del candidato en transacción a base local vacía y esquemas managed; insertar únicamente fixture A owner, B editor, C outsider, key fingerprint ficticio, gate false, ventana false. No se cambia CHECK hard closed, no se habilitan ventanas. Reload cache PostgREST. Cuentas no son las del proyecto remoto. No crear cartas, ni copiar datos, ni poblar storage.objects directamente.
Verificar RLS 12/12, ACL efectiva y revocación legacy, rol dedicado, ausencia de PUBLIC EXECUTE, bucket privado 4MiB octet-stream. Para cada actor: login por Auth real, verificar JWT sub/session_id y getUser, confirmar fila auth.sessions; probar helper privado bajo rol dedicado con ventana cerrada (A/B aceptan contexto, C deniega); llamada RPC por service local debe devolver 42501 certification denied, demostrando que PostgREST resuelve RPC real; llamadas anon/authenticated y legacy denegadas; Edge candidata manifest 403 genérico no-store/CORS; Storage API directa upload denegada; logout local y SQL 0 sesiones; helper rechaza sesión revocada. Listar bucket por service local y exigir vacío, auditoría final 0 fences/ops/heads/objects. No transferencias positivas; no prueba causación del 403 Edge por fencing o sesión, gate/window cierran antes. Prueba natural expiry/replay del runtime queda E.4. Contexto helper aislado no autoriza acceso a cartas.
Cleanup supabase stop --no-backup únicamente en proyecto temporal propio y runner desechable. Si falla, job FAIL; runner no reutilizado. No ejecutar este harness en equipo de usuario ni stack compartido. Sin migración hosted, deploy, merge, gate abierto ni proyecto cloud nuevo.
