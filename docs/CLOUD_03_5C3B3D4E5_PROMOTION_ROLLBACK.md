### Evidencia de la plataforma
La KB oficial https://supabase.com/kb/troubleshooting/permission-errors-when-granting-custom-roles-access-to-the-auth-schema-9e32e7 explica que USAGE sin grant option no se puede delegar, los roles managed son reservados y recomienda funciones privadas SECURITY DEFINER pequeñas de postgres, incluso para locks Auth cuando son necesarios. Las restricciones desde 21/04/2025 permiten políticas RLS en auth.sessions/storage.objects en principio (https://supabase.com/changelog/34270-restricting-access-on-auth-storage-and-realtime-schemas-on-april-21-2025); no inferir imposibilidad absoluta de CREATE POLICY a partir de ownership solamente, ni asumir que el grant a rol custom funcione. No cambiar ownership managed: https://supabase.com/docs/guides/platform/permissions. Auth session_id debe comprobarse contra fila real, y presencia por sí sola no garantiza vigencia: https://supabase.com/docs/guides/auth/sessions. Consulta read-only real: postgres tiene USAGE auth/storage, SELECT id/user_id/not_after de auth.sessions, UPDATE(id) efectivo sin grant option, SELECT bucket_id/name/metadata storage.objects. Estos permisos hacen viable investigar puente privado sin modificar managed. No ejecutar locks de comprobación remotos en esta etapa.
